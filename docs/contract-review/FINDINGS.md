## Workspace applicability evidence

`listClaudeCodeWorkspaceGroups` groups discovered/coalesced transcripts with content. `listKiroWorkspaceGroups` groups merged continuation transcripts. `listClineWorkspaceGroups`, `listGrokWorkspaceGroups`, `listFxWorkspaceGroups`, `listMiniMaxCodeWorkspaceGroups`, and `listCommandCodeWorkspaceGroups` derive their visible groups from session/task records. `listQoderWorkspaceGroups` groups record summaries; `listAntigravityWorkspaceGroups` passes discovered conversations and project labels to `groupAntigravityConversations`.

These functions support treating **removal of a Spiracha virtual group independent of its conversations** as not applicable. They do not authorize deleting an application's entire project/cache directory. Workspace-wide conversation deletion remains applicable and must enumerate the authoritative group membership, not only the current filtered page. Native workspace cleanup must be enabled only for explicitly owned native metadata with tested handlers. For Antigravity and Qoder, preserve external project/task metadata unless exclusive ownership is proven.

## Important limits of this foundation

The catalog intentionally contains identity, route, scope and export identity only. It does **not** pretend all capability decisions are resolved. `Capability`/`CapabilityBinding` supply a type-level building block and negative fixtures; they do not yet enforce UI reachability or raw/delete capability checks. The adapter's optional raw/delete members remain pending the complete operation migration. The original raw allowlists in the dialog/server are not yet capability-derived. No source was newly declared unsupported to make a gate pass.

No deletion algorithm, data-discovery location, external process interaction, source normalizer, payload artifact extraction, generated route tree, dependency version, or lockfile is changed by these foundation patches. Current normalized-export defaults remain unchanged. Detailed target DTO/default changes in `docs/source-adapter-contract.md` are future work, not claims about this build.

## Review risks to carry forward

Base64 is a lossless transport encoding, not a new export format. It expands inline data by approximately one third before browser decoding. The existing configurable large-export threshold now bounds the raw inline path; above it a single selection becomes a ZIP. The broader archive layer still reads ZIP content into memory and needs explicit aggregate-byte admission and cancellation cleanup tests. Do not equate age/quota pruning before an export with reservation of bytes for an in-flight export.

The full original Bun/React/TanStack graph could not be checked here. Review the stored verification results before relying on this patch in a release. The source-backed plan deliberately leaves narrow, named investigation gates for storage ownership that the archive cannot establish safely, rather than inventing deletion rights or production exceptions.
