# Grok Bot deletion recovery

Deletion is offline: quit Grok Bot and keep it stopped throughout deletion and recovery. The process check fails closed when unavailable, but is a point-in-time observation, not an atomic exclusion against relaunch. Spiracha does not control the external application's writer or claim cross-process atomicity with it.

Before changing the roster, Spiracha writes and fsyncs a private `.spiracha-delete-<digest>.json` receipt in the persistence directory, then syncs its directory. The digest binds the account and conversation. Version 1 receipts contain the original row and replica identity (device, inode, size, modification and change times). They contain no caller-supplied deletion paths. An interrupted receipt write leaves only a temporary file and cannot authorize deletion. Roster replacement is atomic and synced; only then is the original replica removed and its directory synced. Completion removes the receipt and syncs again.

Retry the same delete request to resume after interruption, including when the roster row is already absent. The stable client/API retain `deletedIds` when the row was removed and report residual cleanup in `cleanupFailures`. The UI keeps the delete dialog open with the cleanup error so Delete can be retried. After restarting the UI, retry through the same chat URL or the client's `deleteConversation({ source: 'grok-bot', id })` operation. No read/list request mutates source storage. Once cleanup and receipt removal finish, a later retry is a no-op.

Recovery re-reads the active account and original row and rejects changes to the target row or replica identity, malformed receipts, and nonregular files. It preserves sibling rows, unknown roster fields, other accounts, and other replicas. A changed account must be restored before retrying that account's cleanup. Inspect an unresolved receipt rather than modifying it to force recovery: a recreated chat or changed replica may represent new work. Same-server deletes are queued and a SQLite writer lock serializes independent Spiracha processes across the entire mutation and recovery. A process exit releases the lock; the app does not participate in it and must stay stopped. File identity checks detect observed changes and do not claim exclusion against an uncooperative concurrent writer.

There is no legacy migration or compatibility facade. Earlier partial deletions that have no durable receipt cannot be safely inferred as authorized cleanup. Tests cover roster replacement failure, replica removal failure, idempotent retry, and actual process exits after each persisted deletion phase.
